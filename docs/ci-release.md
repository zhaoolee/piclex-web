# CI 与发布检查

2026-11-05 用户明确要求：修复完整流水线后再发布，避免连续推送导致失败邮件刷屏。

## 推送前

1. 检查远程 main、当前工作区以及正在运行的 Actions；保留其他任务的未提交修改。同一批修复集中验证后推送，不用推送试错。
2. 在独立候选源码中使用锁定依赖，完成改动及相邻流程的定向检查。受影响模块的功能回归和完整性能验收由同一次正式 `Check release candidate` 执行，未变化模块复用下文列出的已验证基线，默认不在本地复制完整套件。正式 CI 使用 Ubuntu、Node 24，以及 Playwright 锁定版本对应的 Chrome/WebKit；本机 Mac 定向检查不能替代它。
3. 涉及浏览器、测试或兼容性问题时，先在隔离、静音的 Linux 环境复现失败用例，修复后验证原用例及相邻流程。候选收敛后集中推送，运行按累计影响范围选择的回归；不跳过失败测试、降低有效断言或靠连续重跑碰运气。

```sh
npm ci
npm run decks:build
git diff --exit-code -- tests/fixtures/demo
npm test
npm run test:deploy
npm run content:build
npm run build
npx playwright install --with-deps chrome webkit
# 按改动选择对应用例；这里以备份和同步为例。
CI=1 npm run test:browser -- tests/browser/webdav-backup.spec.ts
```

上面是开发阶段的准备与定向检查示例。流程为：**构建一次 → 受影响模块功能检查与独立卡顿测量并行 → 保存合格网页及镜像 → 发布时复用同一产物 → 线上版本及相关行为确认**。卡顿门禁按 [性能验收要求](web-performance-release-gate.md) 完成全部24轮，不能用本地定向检查、功能测试或旧版本结果代替。

## 推送与收尾

- 推送前再次核对远程是否被其他任务更新；有更新则核对差异并验证受影响部分，不强制推送。
- 同一批改动集中推送一次，记录精确提交 SHA。已有同提交完整验证可以复用，不重复触发。
- 等待该提交的 `Check release candidate` 中 build、全部六个浏览器分片、`Performance release gate` 和镜像准备全部成功，产物及证据未过期后才可上线。候选准备完成不等于网站已更新。
- 对照正式 Pages 页面及其脚本、样式资源，记录完整测试数量、既有跳过项及结果链接。
- 两站的版本、资源和改动及相邻行为确认可并行；复用同提交的完整功能和性能证据，不再复制整套验收。期间若版本变化，必须重新核对证据对应关系。
- 失败时先下载具体失败日志和 trace，在对应环境复现；有已验证的修复再推送，不边等失败边继续推同一问题的尝试。
- 不关闭失败通知来代替修复。测试已显式声明的平台不适用项与新失败要分别记录。
- 收尾记录放在现有工作流忽略的 `docs/`、`memory/` 等路径内；先核对实际差异，避免记录提交再次触发部署。

## 本次失败中的测试经验

- Playwright 请求拦截会禁用 HTTP 缓存。慢网资源显示检查与正常缓存复用检查必须分开；缓存检查按实际传输字节判断，不能同时拦截请求再要求缓存命中。
- 等待后台图片预热的实际完成事件，不能把 `networkidle` 当成 `requestIdleCallback` 已执行的证据。
- 等待照片动画及视口 CSS 状态真正更新，再断言位置；画布像素检查固定物理像素密度。
- 操作触发整页刷新时，先订阅并等待新文档加载，再确认目标页面标题及操作结果。元素数量为零也可能只是刷新中的空白文档，不能据此立即跳转下一页。
- 按平台选择浏览器启动参数；Linux WebKit 不接受 Mac 的 `--mute-audio` 参数。
- 界面结构变化后更新定位方式，保留原本要保护的交互、布局、数据及缓存行为。

## 构建复用与并行检查（2026-11-08）

- 应用和公开卡组只在 `build` 中生成一次，上传同一份 `github-pages` 产物。desktop、mobile、mobile-webkit 各自执行 `--shard=1/2` 和 `2/2`，共六台独立 runner；每台仍两个 worker、零重试，只安装所需浏览器。测试断言、用例及既有跳过条件不变。
- `Performance release gate` 使用另一个独立 runner 和同一份产物，完整执行桌面/触屏各四场景三轮。功能测试不与性能测量争用同一台机器；任何一轮失败、缺项或版本错误都阻止候选资格和后续上线。
- Docker 主线发布由 Pages 工作流调用，逐文件核对同提交产物的大小与 SHA256 后直接打包 Nginx 镜像，不再次下载卡组或编译。容器集成检查与 AMD64/ARM64 发布保留。标签及手动 Docker 入口只复用同提交已经通过全部六分片及性能门禁的产物；缺少有效证据时拒绝发布。
- 仅工作流、测试、文档及上述 CI 打包辅助文件变更时，按影响范围检查浏览器；未变化模块复用基线，不重新采样产品性能或准备发布镜像。这类运行的性能作业为 skipped，因此发布校验器会拒绝它，不具备发布资格；应用、内容和常规运行配置变更照常发布。`workflow_dispatch` 可显式进行正式发布。分类逻辑与产物校验有独立测试。
- 每个分片保留独立的 `browser-results-<project>-<shard>` 截图、trace 和 blob 报告；性能原始记录保存在 `performance-results`。正式完成需六个分片及性能作业全部成功，不以局部通过代替全套。

## 已验收产物的快速发布

候选流水线只准备网页与带SHA的双架构镜像，不切换Pages或Docker latest。正式发布使用 `Release verified build`，输入候选的完整40位提交SHA。它验证全部六分片、24轮性能、容器验证以及产物有效期；网页逐文件校验后部署，Docker按不可变digest切换latest，不重新编译镜像。两项并行，随后检查实际网页资源/导入与模块切换及镜像digest/架构。

```sh
gh workflow run release.yml --ref main -f revision="$RELEASE_SHA"
```

目标是发布触发到所需线上确认完成不超过120秒，包含GitHub排队；实测前不保证该数字。完整候选准备时间单列，未准备好时不允许发布，不将失败检查排除计时后冒充成功。国内站仍使用现有标准更新器和完整文件/安全清理校验；当前sudo要求密码且没有CI部署凭据，此部分尚未自动化，不能将Pages/Docker成功称作双站目标达成。


## 按模块选测（2026-11-08）

`browser-test-scope.mjs` 使用一张小型显式映射表，支持学习输入/语音/样式、相机、游戏及跨模块经验组件。混合模块 spec 整份执行，保留原来的桌面/触屏/WebKit适用范围、六分片、断言与零重试。共享存储、公共样式、依赖、构建配置、测试辅助文件及未知文件回退全量；修改 spec 直接执行该 spec，删除 spec 回退全量。

功能基线是 [CI 42452360890](https://github.com/zhaoolee/piclex-web/actions/runs/42452360890) 的 `2e2cc76ba0973b8f81673c8bef4b00f4b80199a2`：build和六个浏览器作业成功（620通过、4项既有跳过）。性能失败仍然有效，绝不继承为发布通过。CI先查询该运行的仓库、SHA、作业状态，再对基线到当前候选做**累计差异**，不是只看最后一笔提交。缺少证据、基线不是祖先或查询失败时回退全量。

本次仅接入选测的 pages.yml 已逐项审查，记录确切SHA256；后续修改这个工作流会使复用失效，须审查新执行环境或跑全量，不自动更新哈希。手工 `full-browser=true` 可明确运行全量；只在新的全量浏览器证据审查通过后更新脚本中的基线，不把局部通过提升为完整基线。

每次运行保存 `browser-scope` JSON产物（基线、当前SHA、选测理由与文件）。空范围保留六个明确的复用回执，不装浏览器。范围非空时，Playwright既有WebKit白名单及分片可能产生合法空分片；仅定向运行允许空分片，全量仍拒绝空集，选测命令拒绝空或畸形文件清单。

产品改动（包括性能测量器改动）仍执行当前版本全部24轮性能门禁。纯工具/测试记录运行跳过性能且无法成为正式发布候选；要发布该SHA，须显式运行候选验收并获得同SHA性能成功，不能使用跳过或旧失败结果。
